# Spike findings — 2026-08-03

Covers S1–S5 from [the build plan](../plans/chorus-build-plan-2026-08-03/plan.md) §6.2.
Everything below was measured against the real tools on this machine
(`codex-cli 0.146.0`, `claude 2.1.220`, Electron 43.2.0), not read from docs.

**Verdict: all five pass.** Four findings change the design and are marked ⚠.

---

## Protocol ground truth — generated bindings vs. published docs

`codex app-server generate-ts --out <DIR>` emits **622 files / 2.5 MB**, with the
current protocol under `v2/`. Every shape below contradicts the published prose
reference, and each one would have been a runtime failure discovered during M2:

| Thing                  | Docs say                              | Actually                                                                                                                      |
| ---------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `thread/start` sandbox | `{ type: 'readOnly', … }`             | `SandboxMode` string enum: `"read-only" \| "workspace-write" \| "danger-full-access"`                                         |
| `turn/start` sandbox   | same as above                         | a _different_ type, `SandboxPolicy` — the object form, with camelCase tags (`readOnly`, `workspaceWrite`, `dangerFullAccess`) |
| `approvalPolicy`       | `never \| unlessTrusted \| onRequest` | `"untrusted" \| "on-request" \| { granular: {…} } \| "never"`                                                                 |
| text input             | `{ type: 'text', text }`              | also requires `text_elements: TextElement[]` — snake_case in an otherwise camelCase API                                       |
| `turn/interrupt`       | "cancel with turn/interrupt"          | requires **both** `threadId` and `turnId`                                                                                     |
| `turn/start`           | implied long-running                  | **returns immediately** with `{ turn: { id, status: 'inProgress' } }`; streaming arrives as notifications                     |

Two consequences:

- ⚠ **`SandboxMode` and `SandboxPolicy` are distinct types with near-identical
  names**, used by adjacent methods. This is a live footgun; the adapter should
  wrap both behind our own `SandboxPolicy` (already in `agent-protocol`) and
  never let either provider type escape.
- The undocumented `{ granular: … }` approval variant exposes per-category
  toggles (`sandbox_approval`, `rules`, `skill_approval`, `request_permissions`,
  `mcp_elicitations`). Worth revisiting in M5 — it may map more directly onto our
  permission profiles than the coarse presets do.

**Committing the generated bindings and diffing them in CI is now clearly
justified** rather than merely prudent (plan §6.1).

## S1 / S3a — Codex: interrupt and crash survival ✅

Setup: temp git repo, `approvalPolicy: 'never'`, `sandbox: 'read-only'`, a turn
long enough to interrupt mid-stream (`gpt-5.6-sol`).

- **Interrupt works cleanly.** `turn/interrupt` returns `{}`, and
  `turn/completed` reports `status: "interrupted"`. Deltas stop immediately.
- **A SIGKILL mid-turn is survivable.** After hard-killing the app-server and
  reconnecting, `thread/resume` succeeded and the thread was intact.
- **Conversational context survives.** Asked after resuming what had been
  requested, the agent answered _"You asked for 1–300 and 301–600"_ — both
  pre-kill turns were still in context.
- ⚠ **Partial assistant output is discarded.** `thread/read` on the recovered
  thread showed both interrupted turns containing **only a `userMessage` item**.
  Every streamed `item/agentMessage/delta` before the interruption was gone from
  the persisted thread.

## S2 / S3b — Claude: interrupt, resume, fork ✅

Run against the SDK installed with `--omit=optional`, so the ~257 MB bundled
binary was verifiably absent (`bundled 257MB binary present? false`) and
`pathToClaudeCodeExecutable` pointed at the installed `claude`.

- **§2.5 is validated end to end.** Driving the installed CLI with no bundled
  binary works, using existing auth.
- **`interrupt()` works** in streaming-input mode.
- ⚠ **An interrupt surfaces as an error.** The final result message is
  `subtype: "error_during_execution"`, `is_error: true` — there is no
  "interrupted" status. Codex, by contrast, reports `interrupted` explicitly.
- ⚠ **Partial assistant output is preserved.** After resuming, the agent
  reported _"I got to 175 before you interrupted"_ — the partial text was in
  session history.
- `resume` keeps the **same** `session_id`; `forkSession: true` yields a new one.
  Both behave as documented.

### ⚠ The asymmetry that matters most

|                                   | Codex         | Claude                                |
| --------------------------------- | ------------- | ------------------------------------- |
| Partial output after interruption | **discarded** | **preserved**                         |
| Interrupt status                  | `interrupted` | `error_during_execution` + `is_error` |

Two design consequences, both for M1/M2:

1. **Chorus's event log must be the source of truth, not the provider's.** We
   cannot rebuild a transcript from `thread/read` after a crash, because Codex
   will not return what the agent already said. Deltas must be persisted as they
   arrive. This promotes the event store from "good for audit" to **load-bearing
   for crash recovery**, and it is the single strongest argument for the
   append-only design in §4.3.
2. **The adapter must map a user-initiated interrupt to `interrupted`, not
   `error`.** That means tracking whether _we_ requested the interrupt, because
   Claude's wire signal for "user stopped it" is indistinguishable from a real
   failure. Showing an error card for a button the user just pressed would be a
   bug in the most-used interaction in the app.

## S4 — better-sqlite3 in Electron ✅ (better than expected)

- ⚠ **No rebuild step is needed.** `better-sqlite3@13.0.2` ships N-API
  `prebuilds/` including `darwin-arm64`, and `require()` succeeded inside
  Electron 43 (module ABI 148) with **no `@electron/rebuild` run at all**. The
  plan assumed a native rebuild against Electron's ABI; that assumption is
  obsolete. No native build toolchain in CI, and one less thing to break on
  Electron upgrades.
- WAL mode enables correctly.
- **10,000 rows inserted in ~18 ms** in a single transaction (~550k rows/s).
  This settles §3.1: synchronous SQLite on the main process thread is not a
  latency concern at our write volume.
- The backup API works — but **`backup()` is async while everything else is
  sync**. Easy to get wrong; the pre-migration snapshot path in M1 must await it.

Still outstanding for M9 (deferred): the `.node` binary must be signed
individually for notarization. Not testable without a Developer ID.

## S5 — Renderer under a fast token stream ✅ (with a caveat)

6 s per mode, ~5,000 tokens/s, 200-message backlog, measured via rAF deltas.

| Mode                       | p50    | p95    | p99    | max         | dropped | React renders |
| -------------------------- | ------ | ------ | ------ | ----------- | ------- | ------------- |
| naive (setState per batch) | 8.3 ms | 9.2 ms | 9.4 ms | **74.6 ms** | 1       | 1,213         |
| coalesced (rAF flush)      | 8.3 ms | 9.2 ms | 9.4 ms | **9.5 ms**  | 0       | 719           |

- ⚠ **The frame budget is 8.3 ms, not 16.7 ms** — this display runs at 120 Hz.
  The plan's "< 16 ms" target was written for 60 Hz and is too lenient. Both
  modes still meet the stricter bar at p99.
- Coalescing's win is **the tail, not the median**: it removes the 74.6 ms spike
  and cuts renders ~40%. React 19's automatic batching already absorbs most of
  the median cost, which is why naive looks deceptively fine.
- ⚠ **`requestAnimationFrame` stops in hidden or occluded windows.** Discovered
  the hard way — the harness produced no results until the window was shown.
  A coalescing strategy built purely on rAF will **stall and buffer without
  bound** whenever Chorus is backgrounded, which is exactly when a long agent
  turn is most likely to be running. The implementation needs a time-based
  fallback flush and a bounded buffer, per §4.6's drop rules.

**Caveat on this result.** The harness renders plain text nodes. The real
transcript adds markdown parsing, syntax highlighting, and virtualization, all of
which land on the naive path far harder. This proves coalescing is cheap and
sufficient _at this fidelity_; it does not prove the real transcript is fine.
Re-run as an M4 exit gate against the actual component.

## Net effect on the plan

| Finding                              | Changes                                                                                               |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| Partial-output asymmetry             | §4.3 — event log is load-bearing for recovery, not just audit. M1 must persist deltas as they arrive. |
| Interrupt reported as error (Claude) | §4.2 — adapter tracks user-initiated interrupts to disambiguate                                       |
| `SandboxMode` vs `SandboxPolicy`     | §4.1 — neither provider type may escape the adapter                                                   |
| No native rebuild needed             | §2.4, §6.2 — S4's premise obsolete; simpler CI                                                        |
| rAF stalls when backgrounded         | §4.6 — coalescing needs a time-based fallback and bounded buffer                                      |
| 120 Hz frame budget                  | §6.2 — S5 target tightened from 16 ms to 8.3 ms                                                       |
